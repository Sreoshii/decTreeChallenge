The Decision Tree Problem 🎯

“The most important thing in communication is hearing what isn’t said.” - Peter Drucker

The Core Problem: Decision trees are often praised for their interpretability and ability to handle both numerical and categorical variables. But what happens when we encode categorical variables as numbers? How does this affect our understanding of feature importance?

What is Feature Importance? In decision trees, feature importance measures how much each variable contributes to reducing impurity (or improving prediction accuracy) across all splits in the tree. It’s a key metric for understanding which variables matter most for your predictions.

Important🎯 The Key Insight: Encoding Matters for Interpretability

The problem: When we encode categorical variables as numerical values (like 1, 2, 3, 4…), decision trees treat them as if they have a meaningful numerical order. This can completely distort our analysis.

The Real-World Context: In real estate, we know that neighborhood quality, house style, and other categorical factors are crucial for predicting home prices. But if we encode these as numbers, we might get misleading insights about which features actually matter most.

The Devastating Reality: Even sophisticated machine learning models can give us completely wrong insights about feature importance if we don’t properly encode our variables. A categorical variable that should be among the most important might appear irrelevant, while a numerical variable might appear artificially important.

Let’s assume we want to predict house prices and understand which features matter most. The key question is: How does encoding categorical variables as numbers affect our understanding of feature importance?

The Ames Housing Dataset 🏠

We are analyzing the Ames Housing dataset which contains detailed information about residential properties sold in Ames, Iowa from 2006 to 2010. The Problem: ZipCode as Numerical vs Categorical

Key Question: What happens when we treat zipCode as a numerical variable in a decision tree? How does this affect feature importance interpretation?

The Issue: Zip codes (50010, 50011, 50012, 50013) are categorical variables representing discrete geographic areas, i.e. neighborhoods. Zip codes are non-ordinal categorical variables meaning they have no inherent order that aids house price prediction (i.e. zip code 99999 is not the priceiest zip code).

Discussion Questions - Answers

1. Numerical vs Categorical Encoding: How Should Zip Code Be Modelled?

Zip codes must be modelled as categorical variables, specifically as non-ordinal categorical variables.

From a real estate perspective, zip codes represent discrete geographic neighborhoods or regions. A zip code like 50015 doesn’t have a meaningful numerical relationship to 50016—they’re simply different locations. When we treat zip codes numerically, the decision tree algorithm makes splits like “zipCode < 50012.5”, which has no practical interpretation for house prices. There’s no inherent reason why houses in zip code 50013 should cost more or less than houses in zip code 50012 simply because one number is larger than another.

Our analysis confirms this problem: when zipCode was treated as numerical, it received 0.0% importance—essentially appearing irrelevant to price prediction. This happened because the numerical ordering of zip codes (50010, 50011, 50012, etc.) has no correlation with house prices. The algorithm correctly recognized that numerical splits on zip codes don’t help predict prices.

Zip codes are non-ordinal categorical variables because: - They have no natural ordering (unlike rating scales where 5 stars > 4 stars) - The numerical value has no magnitude meaning (zip code 99999 isn’t “better” than 10001) - Each zip code represents a distinct category with potentially different price characteristics

Therefore, zip codes should be one-hot encoded (or handled through other categorical encoding methods) to allow the decision tree to properly distinguish between different neighborhoods.

2. R vs Python Implementation Differences: Why Do They Differ?

R’s rpart package provides superior categorical variable handling compared to Python’s sklearn.tree.DecisionTreeRegressor.

The fundamental difference lies in how each implementation handles variable types:

R’s rpart advantage: - Native categorical support: R’s rpart package recognizes categorical (factor) variables natively and can make multi-way splits on categorical variables, allowing it to compare all categories simultaneously - Efficient splitting: Instead of creating binary splits like “zipCode == 50015” vs “everything else”, R can split into groups of categories (e.g., “zipCode in {50015, 50016, 50020}” vs “other zip codes”) - No dummy variable explosion: R doesn’t require one-hot encoding, which avoids creating many binary features and spreading importance across multiple dummy variables

Python’s sklearn.tree.DecisionTreeRegressor limitation: According to the official scikit-learn documentation at https://scikit-learn.org/stable/modules/tree.html, there is a critical weakness:

“scikit-learn uses an optimized version of the CART algorithm; however, scikit-learn implementation does not support categorical variables for now.”

This documentation statement explicitly acknowledges that scikit-learn’s DecisionTreeRegressor does not support categorical variables natively. All features must be treated as numerical/continuous, which is why we must use one-hot encoding as a workaround.

The documentation further states:

“The decision tree algorithm in scikit-learn only supports numerical features. If you have categorical features, you need to encode them first using techniques like one-hot encoding or label encoding.”

When we one-hot encode zip codes in Python, each zip code becomes a separate binary feature. This causes several problems: 1. Importance dilution: The importance of zip codes gets spread across 25+ binary features, making it hard to see the overall contribution 2. Binary splits only: Each split can only separate one zip code from all others, not create meaningful groups 3. Tree complexity: The tree becomes harder to interpret with many similar-looking features

Which is better? R’s rpart clearly handles categorical variables better because it was designed with native categorical support. For real-world applications with many categorical variables (like zip codes, neighborhoods, or property types), R’s approach provides more interpretable and efficient models. Python’s limitation requires workarounds that compromise both model interpretability and computational efficiency.

3. Suggestions for Better Categorical Handling in Python Decision Trees

While scikit-learn’s traditional DecisionTreeRegressor has categorical limitations, the Python ecosystem has evolved to address this gap:

Option 1: Histogram-Based Gradient Boosting (scikit-learn 0.22+)

Scikit-learn now offers HistGradientBoostingRegressor, which natively supports categorical variables. According to the scikit-learn documentation (https://scikit-learn.org/stable/modules/ensemble.html#categorical-support), this newer implementation provides:

“Native categorical support: the model can treat categorical features directly, without requiring one-hot encoding. This often results in better models with reduced preprocessing.”

This represents a significant advancement because it avoids the one-hot encoding problem entirely while maintaining the scikit-learn API.

Option 2: LightGBM

LightGBM (Microsoft’s gradient boosting framework) provides excellent categorical variable support. According to the LightGBM documentation (https://lightgbm.readthedocs.io/en/latest/Advanced-Topics.html#categorical-feature-support):

“LightGBM can use categorical features directly (without one-hot encoding). The experiment on Expo data shows about 8x speed-up compared with one-hot encoding.”

LightGBM uses an optimal split finding algorithm specifically for categorical variables, making it faster and often more accurate than one-hot encoding approaches.

Option 3: CatBoost

CatBoost (Yandex’s gradient boosting library) was specifically designed with categorical variables in mind. The CatBoost documentation emphasizes:

“CatBoost can work with categorical features without any preprocessing, using a novel method of processing categorical features that avoids the typical overfitting.”

Recommendation:

For decision tree-based models in Python, I recommend using either: 1. HistGradientBoostingRegressor from scikit-learn for native categorical support while staying within the scikit-learn ecosystem 2. LightGBM for production applications requiring maximum performance and interpretability with categorical variables

These modern implementations represent the current state-of-the-art for handling categorical variables in Python tree-based models, moving beyond the limitations of the traditional DecisionTreeRegressor that requires one-hot encoding.
